Corrective RAG 的解决思路
这张图暗示的优化方向是： 在"检索"和"生成"之间插入一道文档质量校验关卡——先判断检索到的文档是否真的能回答问题（区分 Accurate / Inaccurate），再决定怎么用，而不是无条件照单全收。
CRAG 的具体做法：
1.
检索文档后，用 LLM 评估每个文档的相关性和准确性
2.
如果文档相关且准确 → 直接用于生成
3.
如果文档不相关或不准确 → 丢弃，或触发补充检索（Web 搜索等）
4.
如果所有文档都不准确 → 重写查询重新检索，或回答"无法确定"
一句话总结

传统 RAG 假设"检索到的就是对的"，CRAG 则质疑"检索到的真的对吗？"
这张图的核心警示：检索相关性 ≠ 答案准确性，必须对文档做二次验证，否则会把"看似相关但实则错误"的信息喂给 LLM，导致 confidently wrong（自信地犯错）。

2、核心定义
Corrective RAG（修正增强检索） = 标准 RAG + 检索质量校验 + 自动修正 / 补充检索。它解决标准 RAG 最大痛点：

检索到的文档不相关、不完整、错误 → 导致大模型回答胡说八道（幻觉）

3、工作流程
1）用户提问
2）初步检索：从知识库召回相关文档
3）检索质量评估（CRAG 灵魂）：用一个轻量级检索评估器（Retrieval Evaluator）给每篇文档打分，把整体检索结果归为三类：


4）最终回答：根据评估结果组合"内部精炼知识 / 外部搜索知识 "，用可靠信息生成答案。
4、为什么要用 Corrective RAG？
•
大幅降低回答幻觉
•
对私有知识库 + 公共知识混合问题效果极好
•
比普通 RAG 更鲁棒（健壮）、更准确
5、CorrectiveRAG（CRAG）属于检索后优化阶段
CorrectiveRAG（CRAG）属于 RAG 架构的检索后优化阶段（Post-Retrieval Phase），具体来说是在检索结果评估与修正阶段。
